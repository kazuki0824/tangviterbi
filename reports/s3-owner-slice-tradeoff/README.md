# ② packingの細分化でownerを早くSPIへ戻せるか

2026-10-27。S6/16・16KiB・1024word準備を固定し、packingの1回の処理量だけを比較した。実Cの出力一致・経路保存則を、4 bank長×2開始位置×5 slice量、各64bankで確認。SDK CFGの係数を使い、host実行時間はS3時間へ転用しない。

| pair/slice | core0上端：管理ΔE=0 / 200cycle | core1上端 | core0の非空slice平均時間のケース上端 | 仮定するowner頻度のケース上端 |
|---:|---:|---:|---:|---:|
| 64 | 185.31 / 195.07% | 158.11% | 7.16µs | 119844/s |
| 128 | 126.51 / 131.39% | 113.95% | 10.54µs | 61315/s |
| 256 | 99.63 / 102.41% | 91.35% | 17.29µs | 33333/s |
| 512 | 94.70 / 97.48% | 79.94% | 28.10µs | 33333/s |
| 1024 | 92.24 / 95.02% | 74.89% | 49.96µs | 33333/s |

従来の512結果と同じ条件で再現できた。256は処理単位を短くするが、追加管理200cycle/反復という感度点ではCPU超過。64/128は両coreで超過。1024はCPUを減らす一方、連続packing時間を長くする。**この模型では、細分化だけで時間配分とCPU予算を同時に解消できていない。** 実機で全候補が不可能と証明した意味ではなく、512を維持して処理本体・SPI呼出し費用・スケジュールを改善する必要がある。

頻度を固定して細分化の費用を落とさないように、各ケースでowner頻度をmax(33333.33/s, core0の非空packing slice数/s)とした。1反復1sliceのため後者は必要な平均頻度。実際のempty pollはさらに増え得る。従来の25000/sからの増分を1500cycle/反復、準備管理をΔE=0/100/200/300cycleで課金する。1500とΔEは未測定の感度値であり、U0/U1=20/10 Mcycles/s、α=1.1、API=20µsも仮定を維持する。

表の時間は**非空slice平均**であり、1回の最大時間ではない。fill、7回のRF poll、collect、SPI、IRQを含むowner反復の上限ではなく、30µs scan・公開320µsの達成認定には使わない。正式性能合格・通信路割当・採用は0。

再現：`python -m experiments.s3_owner_slice_tradeoff`。全40条件、CPU感度と入力hashはpaths.json / results.jsonに保存。

## 次の改善に必要な量

256pair案で管理ΔE=200cycle/反復を維持する場合、core0上端の2.4113ポイント超過を消す必要がある。他条件固定でSPI APIのCPU使用時間だけを変えるなら、20→**16.0493µs/転送以下**が100%境界。これは達成を見積もった数値ではなく、必要条件の逆算である。64/128ではAPI費用を0にしてもこの模型のcore0超過が残り、core1も超過する。512では同じ境界が24.1275µsとなり、現仮定20µsは平均CPU予算に入るが、処理間隔の問題が残る。

次に検証する対象はSPIの実CPU費用と非一様なservice間隔。この16.05µsをそのまま転送間隔Gやowner反復時間へ流用しない。式は `20+(100-core0_percent_at_E200)/(100e6/16384*100/1e6)`。負値は必要時間ではなく、API削減だけでは足りないという代数上の診断値。


## 2026-10-28：追加scan側の改善目標

SPI完了転送のAPI費用を20µsに据え置いても、追加scan費用を減らす選択肢がある。管理ΔE=200cycle/反復を固定し、全8ケースを満たす追加scan費用の最大値を逆算した。

| pair/slice | 追加scanのcycle/回上限 | 判断 |
|---:|---:|---|
| 64 | −975.410 | 追加scanを無償にしても平均CPU超過 |
| 128 | −743.002 | 同上 |
| 256 | 805.544 | 1500から694.456cycle/回の削減が必要 |
| 512 | 2225.546 | 現仮定1500は平均CPU内 |
| 1024 | 2935.546 | 平均CPU内だが連続処理が長い |

式は各ケースで `1500+(100-P200)*2400000/(owner_frequency-25000)`、全ケースの最小値を採用。逆代入して各sliceの最大占有率が100%になることを確認した（scan-budget-checks.json）。100%境界は余裕ゼロであり、この値だけで採用しない。

[SPI guardの実命令比較](../s3-spi-running-guard/README.md)はこの追加scan側の一部分を減らす。しかし38〜40命令という値に7回のRF poll、collect、feed、owner管理等は含まれず、805.544cycle/回の達成証明にはならない。転送APIとscanを同時に減額する二重計上はしない。現設定512pairとCPU感度値は維持する。
