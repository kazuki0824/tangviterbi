# ② S側packing非等分化：実C実装と条件付き再見積もり

2026-10-27。前提・確度は[統合見積もり](../receiver-estimate-20261027/README.md)を継承。①は変更しない。

## 結果

S core0の101.58〜106.53%を改善する最初の具体策として、packing境界をビルド時に選択できるようにした。`S3_PP_CORE0_SIXTEENTHS=5`ならcore0が5/16、core1が残り11/16を担当する。pair単位で切り、端数はcore1へ渡す。各pairの出力位置は従来通りで、デシメート・再量子化・payloadコピーは増やさない。既定値8は従来の等分のまま。struct・公開API・bufferサイズを変えず、実機採用設定へ自動変更しない。

**中間条件の平均CPU模型では5/16案が最も均衡し、両coreに約13%以上の余裕がある。実機時間やbank期限の成立確認ではない。** 一様比例による移管計算だけで済ませず、変更した実Cを走らせ、境界処理・slow pair・slice回数を数え直した。

| core0 / core1の担当 | S core0占有率 | S core1占有率 | 最大bankのslice回数 core0/core1 |
|---|---:|---:|---:|
| 8/16 / 8/16（既定） | 101.58〜106.53% | 59.12〜63.77% | 8 / 8 |
| 7/16 / 9/16 | 95.06〜100.01% | 66.14〜72.52% | 7 / 8 |
| 6/16 / 10/16 | 88.05〜92.28% | 73.15〜79.83% | 6 / 9 |
| **5/16 / 11/16** | **81.11〜84.61%** | **79.94〜86.61%** | **5 / 10** |

条件は240MHz、512 pair/slice、α=1.1、SPI CPU active 20µs/32KiB、U0/U1=20/10 Mcycles/s、fillはcore0。各占有率の幅は12288/12289/14288 sample×開始位置0/16380の6列を各64bank走らせた範囲。信頼区間・最悪値ではない。実Cの経路回数に保存CFGの45命令/block、118/run、173/slow pair、213/sliceを適用した模型で、新target binaryの命令計数ではない。変更したcut計算や現wrapperとの差分はU内に収める条件。

## bank期限への接続

非等分化で旧「最大8 slice/core」を流用するとcore1の仕事を過小評価する。`s3_worker_response.worker`と`bank_response`に分担比率を渡せるようにし、workerごとの最大pair数からslice数を導出する。非等分なのにworker番号を省いた呼出しは拒否する。

5/16案の各core最大slice数は5/10。これは定常bank長12288〜14352、carry有無の全整数条件を列挙して再確認した。初回短bankもこれより小さいが、その到着時刻・準備条件は別。

応答式の基礎量は `C_w + (q+1) × n_w × max(C_w,A_w)`。従来の8をそれぞれ5/10へ置き換える。qは古いbank数、Cは通常反復上限、Aはadmission予算。公開遅れ・IRQ等を加え、両DONEの後にcore0のcollect費用を加算し、Sの保守的reclaim期限455.450µsまでに解放する必要がある。APIの数値入力に根拠がないため、この実時間判定を合格扱いにはしない。

参考として5/16案のpackingのみの模型上の平均service時間/bankはcore0 105.94〜126.60µs、core1 233.27〜270.66µs。64bank平均であり、fill/RF/SPI/割込み・公開待ち・古いbank待ち・collectを含まない。455.450との差を期限余裕と呼ばない。

## 検証・再現

- `python -m experiments.s3_asymmetric_pack`：4分担×24条件×64bank。実Cの全出力を逐次参照値とbyte単位で照合し、経路数保存則も検査。人工時計・逐次worker・即時DMAなので時間試験ではない。
- `test_s3_asymmetric_pack`：5/6/7の各設定で実Cの2 pthread・2000bank、carry、wrap、順序逆転DMA、期限拒否、lease保持、native handoff/停止を検査。加えて応答モデルの5/10・6/9等の回数を確認。
- 既存等分packing、経路計数、統合見積もり、worker応答、reclaim試験も実行。合計20 unittest成功。結果はtests.log。

最初の試験は等分専用の「8回」「24回」assertで失敗した。期待値を設定したpair分担とslice幅から導出し、ジョブ境界・全出力・sequence順の検査を保持して修正した。実受信機の時刻・信号品質を検証したものではない。

## 次の判断に残るもの

5/16は平均CPUの第一改善候補、6/16はcore1の局所仕事量を抑える比較候補。target binaryでの費用・両core/DMA干渉・期限を同条件で比較して選ぶ。保存SDKの等分ELFや旧8-slice応答結果を変更候補へ流用しない。ソースに設定を追加しただけで旧ELFの配置結果を更新済みとはしない。

この変更で転送量・通信路・FPGA負荷は減らない。Sリンクの余裕、FPGA全体logic98.73%・BSRAM100%・速度未達は引き続き独立の課題。正式な受信機採用は0。
