# 「改善する」の適用範囲とscan位相の追加検証

2026-10-27。対象は②のみ。結論は、**検査した模型では16 KiB化により未回収buffer量が減る。一方、16 KiBなら容量を満たすという無条件の主張は誤り。実機での改善もまだ確認していない。** 前の説明はこの区別、特にscan開始位相を明記すべきだった。

## 何が本当で、何が未確認か

| 主張 | 結果・根拠 |
|---|---|
| 同じ模型条件で16 KiB化すると未回収buffer量が減った | 保存54条件を27組に対応付け、27組すべてで減少。3列だけの選択ではない |
| 16 KiB化だけで128 KiB容量内に収まる | **誤り**。元の27条件でも16 KiBの容量合格は20、超過は7。さらに40µs scanの位相で合否が変わる |
| 前回の93 byte余裕 | 公開320µs・scan40µs・交互列・**開始位相0**の有限128bank模型の値として正しい。全位相の最小余裕ではない |
| CPUも軽くなる | 誤り。1転送API20µsなら転送回数増でcore0が6.1035ポイント増える |
| 実機全体の実現性が確認できた | 未確認。実時間、任意arrival/jitter、継続動作、FPGA全体資源/速度は残る |

## 全scan位相の検査

公開320µs、3種類の128bank列を固定し、scan開始位相を240MHzの1cycle単位で1周期すべて列挙した。32/16 KiBの40µs scanは各9600位相、16 KiBの30µs scanは各7200位相。合計79200条件で、探索時間を理由に途中打切りしていない。各実行のbank数128は比較範囲の指定で、無期限運転を証明するものではない。

| 転送 / scan | 入力列 | 超過位相数 / 検査位相数 | 全検査位相での最小残容量 |
|---|---|---:|---:|
| 32 KiB / 40µs | 12288固定 | 9600 / 9600 | −20480 B |
| 32 KiB / 40µs | 14352固定 | 9600 / 9600 | −45032 B |
| 32 KiB / 40µs | 12289/14352交互 | 9600 / 9600 | −37325 B |
| 16 KiB / 40µs | 12288固定 | 0 / 9600 | 10240 B |
| 16 KiB / 40µs | 14352固定 | 0 / 9600 | 920 B |
| 16 KiB / 40µs | 12289/14352交互 | **2772 / 9600** | **−2040 B** |
| 16 KiB / 30µs | 12288固定 | 0 / 7200 | 30720 B |
| 16 KiB / 30µs | 14352固定 | 0 / 7200 | **7872 B** |
| 16 KiB / 30µs | 12289/14352交互 | 0 / 7200 | 14344 B |

2772/9600は発生確率でも見積もりの信頼度でもない。一定周期の位相を列挙した個数。周期自体が変動する場合やbank長の任意の並びを網羅していない。scan内の2port操作は瞬時で、queue API等の経過時間を実機通りに模擬していない。周期30µsを現実装が保証できるかは別に確認する必要がある。

## 実装との対応を確認

模型のscan位相0/2400cycle（0/10µs）で発生したaccept、公開、転送開始、reapの順序を、**実際のs3_parallel_pack.c**へ再生した。実Cのaccept/step/collect/take/completeを呼び、全送信byteを独立したIQ参照式と比較した。

- 16 KiB・40µs・位相0：全有限列を処理できる。
- 16 KiB・40µs・位相2400：4869210cycle時点のacceptで予測どおりBUSY。faultを立てず、未回収payloadを上書きしない。
- 32 KiB・40µs・位相0：233676cycle時点で予測どおりBUSY。
- 16 KiB・30µs・位相2400：全有限列を処理できる。

これは容量・所有権・出力値の実装対応検証。人工時刻の順序を実Cへ与えたもので、S3がその速度で実行できることやRF ABIの確認ではない。最初のBUSYで再生を終了し、その後の仮想超過計算を実Cで継続できたとしない。

新しい位相引数、既存0位相、実C/実SPIの16 KiB経路と再生を含め4 unittest成功（tests.log）。

## 次の候補とCPU費用

**公開320µs・scan30µsの16 KiB案は、今回の全位相比較では容量に7872 B以上残る追加候補。正式採用ではない。** scanを40→30µsにすると毎秒25000→33333.33回へ増えるので、追加の空poll/clock/管理費用を見積もりへ戻す必要がある。

既存の16 KiB中間模型上端core0=90.7115%を出発点にし、元の費用がそのままで、追加scanだけに費用ΔCを課す感度計算なら、

`core0占有率 = 90.7115 + ΔC/288 [%]`

となる。100%未満に保つには追加scan当たりΔC<2675.07cycle（約11.146µs）が必要。既計上のpacking/SPI費用を二重に追加しない。これは費用の許容額で、追加scanがこの額以内という実測結果ではない。Uの元の値も未測定の中間仮定である。前回のworker公開期限条件も引き続き必要で、scan周期だけを書き換えて成立扱いにしない。

## 再現

`python -m experiments.s3_short_transfer_audit` が元の27組比較と79200位相条件を再計算する。結果とsource hashはresults.json。`PYTHONPATH=tests python -m unittest test_s3_short_transfer test_s3_short_transfer_replay -v` で実C対応等を再検証できる。

今回のruntime/RTL変更はなく、模型の位相指定、実C再生試験、条件の訂正を追加した。①は変更しない。
