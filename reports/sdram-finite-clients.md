# ② 到着時刻・T書込み完了・cache空きを接続した競合試験

2026-10-19 JST。実SDRAM controller RTLへ、前回の常時backlogではなく、時刻付き要求を与えた。**受信機全体の実到着列ではなく、有利に均等化した必要帯域の試験**である。仲裁とcache消費はtestbench、K7/depuncture RTL自体は未接続。

## 条件と容量の扱い

Mode 3の1 symbolを160380 clocks＝1039.5 µsとし、各源を有理数accumulatorで均等到着させる。T writeは完了した32 Bだけread可能にし、T read完了で192 B cacheを補充する。空き32 B未満ならT read要求を止める。読み出していない2 symbol前の領域へwriteした場合も検出する。

T/Sの根拠は`experiments/dual_memory_contract.py`のMode 3、階層(1,1)/(1,2)/(11,4)、compact_group_masked。今回のT/Sアドレス列はそのring/scatter配置の再現ではない。管理10 MB/sも標準の必須値ではなく既存見積もりの予約値を保持したもの。全量spillのwriteとreadを両方計上している。

T消費は1 symbolの起動猶予後に28.813853 MB/sで均等に行い、空ならunderrunを数える。これは理想消費器であり、共有K7のburstや3階層配分を再現しない。今回の192 Bは合計cacheで、前回の3×64 Bを階層別に接続したものではない。

各背景源の容量判定は**256未完要求**（in-flightを含む）を試験値として置く。ARIBの要請値や実装済みFIFO容量ではない。最初の超過を失敗として記録し、その後も診断用カウンタで滞留量を観測する。超過後の結果は256深さの実queueで処理できた証拠にならない。データの保持場所・descriptor費用・各源に必要な実容量の割当も未完。

背景はRR、同じ源を最大B要求まとめる。途中でもTは前回同様104 clocks閾値で優先可能。まとめる数Bを1/8/32/64/128で比較する。空の源は飛ばす。期限の比較値は全背景源に1 symbolを与えた試験条件であり、各stage本来のdeadlineを導出済みとはしない。

## 判定と残作業

**128要求を上限としてまとめ、Tを途中で優先できる方式を次の検証候補とする。64要求方式も今回の4 symbol試験では通過した。** 128要求方式は16 symbol（16.632 ms）でもFFT最大未完95、各symbol末の未完数1〜6に留まり、今回の区間で累積増大は観測されなかった。これは無限時間の上界証明ではない。

同16 symbol条件の最大未完数はT write 19、FFT 95、T time-deinterleave相当38、S frame相当16、管理7。T readが可能になってから応答までの最大待ちは115 clocks。T underrun、write前read、未読領域overwrite、試験用1 symbol期限の完了時超過はいずれも0だった。実K7の処理完了期限を確認したという意味ではない。

1/8/32要求方式は**今回の256要求容量では**失敗。容量を増やせばすべて救えるとも、あらゆる容量で不可能とも判定していない。特に32要求方式の最大402を、根拠なく「256を512にすれば全条件で十分」と読み替えない。128方式で得られた各源の最大値も、実burstを入れる前に実装容量として固定しない。

unittest 1 method・内部6条件でデータ/command/定常refresh検査が成功。上表の容量失敗は測定結果として残したものであり、unittest成功を全候補通過の意味には使わない。

この試験の通過を全Mode/GI・全階層・全S変調の保証へ拡大しない。次に必要なのは、実FFT/deinterleave/S frameのburstと依存関係を入れた到着・アドレス列、共有K7の実消費、queue/cacheの所有権と実資源量の確認である。有利なモデルでの通過が得られても、仲裁/cacheのRTL化・全体P&Rへ進むための条件付き候補に留まる。

controller本体は変更なし。PHY、全体資源/STA、S3 WCETは未達。正式性能合格・通信割当・採用は0、①は変更していない。

再現：Icarus/vvpをPATHへ置き、`SDRAM_FINITE_REPORT=reports/sdram-finite-clients.json python -m unittest discover -s tests -p test_sdram_finite_clients.py -v`。

長時間試験で記録配列の上限に達した初回は結果解析エラーとなった。その後、1要求だけin-flightという契約に合わせ、検査用記録を1024 slotで循環再利用するよう修正した。過去の全要求にwide vectorを確保せず、未完要求の記録は上書きしない。試験装置の修正であり、FPGA資源の削減とは計上しない。
